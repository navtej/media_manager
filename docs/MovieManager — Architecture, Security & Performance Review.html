① Fast-search foundations: indexes + debounce + FTS5 over titles and transcripts

Strong

Files

  • lib/data/tables.dart — zero @TableIndex entries in entire schema
  • lib/logic/catalog_controller.dart:308–317 — lower(title) LIKE '%term%'
  • lib/ui/screens/home_screen.dart:43–64 — search fires on every keystroke, no debounce
  • lib/data/database.dart:30–135 — migration site for v11

Problem

Every search is an unindexable leading-wildcard LIKE over videos.title and absolute_path, executed on every keystroke, as part of three stacked queries (rows + full-set aggregates + tag facets) — each a full table scan + temp B-tree sort because the schema defines no indexes at all. Transcript text already persisted by the AI pipeline (video_summaries.transcript_text) is completely unsearchable.

Solution

  1. Migration v11: indexes on folder_id, (file_created_at DESC, id), title, video_tags(tag_id), is_favorite.
  2. Debounce search input 250 ms before setSearchQuery (~10 lines).
  3. FTS5 virtual tables (title; external-content over transcripts) with sync triggers → MATCH 'term*' replaces %term%. Ships “search inside subtitles/transcripts” as a headline feature.

Benefits

  • depthThe FTS query module hides triggers, tokenizer config, prefix semantics behind one search(criteria) interface.
  • leverageIndexes speed every consumer: catalog pages, per-folder scans, tag facets, favorites.
  • testsCatalogQueryModule's existing fake-based tests prove the seam; FTS slots behind it with no UI change.

② Grid card query fan-out: three DB round-trips per card, per rebuild, per hover

Strong

Files

  • lib/ui/widgets/video_grid.dart:1358 — new stream object built inside build() → re-subscribe + SQL join per rebuild
  • lib/ui/widgets/video_grid.dart:1474–1555 — _FolderPathWidget: fresh getAllFolders() FutureBuilder per card
  • lib/ui/widgets/video_grid.dart:609–615 — summary provider keyed by whole Video object does File.exists()+stat() + directory listing just to render a tile
  • lib/ui/widgets/video_grid.dart:244 — cards watch the entire selection state → every checkbox click rebuilds all mounted cards

Problem

Hovering counts as a rebuild. Moving the mouse across a screenful of ~30 cards fires dozens of fresh SQL queries, file stats, and even directory listings — repeated on every scroll page-in. On network drives this is seconds of I/O to render a screen. The folder→path concept has no home (no locality): it's recomputed per widget instance.

Solution

  • Stable StreamProvider.family keyed by video.id for tags (subscription reused across rebuilds).
  • One shared foldersMapProvider (watchAllFolders() → Map<int,Folder>) consumed synchronously.
  • Summary state keyed by video.id; move freshness checks (exists/stat/VTT discovery) behind dialog open, not tile render.
  • Narrow watches with .select((s) => s.isSelected(id)).

Benefits

  • localityFolder-path display logic moves next to the existing path helpers in logic instead of living in a private widget method.
  • leverageOne provider powers every card; N subscriptions collapse to 3 shared ones.
  • testsCard data becomes assertable at provider level without pumping 1819 lines of grid widget.

③ Catalog snapshot: table-granularity invalidation + O(n²) pagination

Strong

Files

  • lib/logic/catalog_controller.dart:135–146 — refetch trigger is a sentinel COUNT(*) watching {videos, videoTags, tagDefinitions}
  • catalog_controller.dart:624–662, 699–714 — loadMore re-fetches all previously loaded pages, then validates the prefix row-by-row
  • lib/logic/library_controller.dart + settings_configuration.dart:202 — scans insert in batches of 4 → ~100 snapshot recomputes while adding a 400-file season
  • Good news: PER-11's CatalogQueryModule is a real, test-substituted seam — this deepens it, doesn't replace it.

Problem

Any row anywhere in three tables rebuilds the entire snapshot (rows + aggregates + facets), unthrottled. During a scan that's a recompute storm racing your scrolling. Loading more re-reads everything already shown: 10 pages of 50 = 2,750 rows read cumulatively for 500 displayed.

Solution

  • Trailing-edge throttle (~300 ms) on the watch trigger; consider drift's TableUpdate granularity later.
  • Keyset pagination: WHERE (sort_col, id) > (?, ?) LIMIT n — append-only reads.
  • Raise scan batch size (4 is tiny); optionally coalesce snapshot refreshes during scans.

Benefits

  • depthThe module's watch/fetch(criteria) interface stays identical; only its implementation gets smarter.
  • localityPrefix-validation machinery (_validateExpandedPrefix, two lists + set per click) simply gets deleted.
  • teststest/catalog_pagination_test.dart (559 lines) already exercises append/retry against a fake — it survives unchanged.

④ Widgets mutate DAOs directly; Tag Management hand-rolls a second copy of the catalog

Strong

  • lib/ui/widgets/filter_bar.dart:87–92 vs tag_management_screen.dart vs video_grid.dart — three different confirmation policies for destructive tag deletes

  • lib/data/database.dart:416–1015 — TagsDao is really a domain service (normalization, rename/merge conflict resolution, statistics) buried in the storage layer

Problem

These widget methods are one-line forwards into DAOs — they fail the deletion test (delete the wrapper, lose nothing). No single place enforces postconditions like “after a tag mutation, prune definitions and refresh stats,” so consequences are re-stated (or forgotten) at each call site, and every flow must be tested through widget pumps with a live DB.

Solution

  • Extract a TagCatalog module from TagsDao (normalize/rename/merge/stats) at the data↔logic seam.
  • Route all UI mutations through thin intent modules (TagMutations/VideoMutations) that own postconditions + status messages.
  • Give Tag Management a criteria/snapshot query like the catalog's — the screen becomes presentation and gains a test surface.

Benefits

  • depth“Rename tag X→Y” becomes one call hiding conflict detection, cascades, pruning.
  • localityDestructive-action confirmation policy lives in exactly one place instead of three divergent ones.
  • leverageUnlocks testing the two worst files (video_grid, tag_management) through interfaces instead of widget pumps.

⑤ Subtitle sidecar matching implemented three times — with three different answers

Strong

Files

  • lib/logic/video_summary_controller.dart:714–769 — exact stem or stem.[a-z]{2}, VTT only
  • lib/logic/video_move_controller.dart:716–745 — startsWith(basename), case-sensitive ext list
  • lib/services/media_deletion_service.dart:98–123 — equal-or-stem.-prefixed, lowercase ext list

Problem

The rule sets concretely disagree. For movie.mp4: movie.en.srt gets moved and deleted but never used as a transcript source; moviex.vtt travels with the video on move but is left orphaned on delete. Predicting what happens to one subtitle file requires holding three modules in your head — low locality, and a real bug class.

Solution

One SidecarLocator module: sidecarsFor(mediaPath) behind a single matcher, parameterized only where genuinely needed (summaries care about VTT-parsability; move/delete care about ownership). Extract alongside the VTT parser currently buried under Riverpod controller code (parseVttTranscript runs in an isolate yet lives below providers).

Benefits

  • locality“Which files belong to this video?” answered in one place; fix once, fixed everywhere.
  • depthTiny interface, heavy matching/parsing implementation hidden behind it.
  • testsMatcher becomes a pure function — table-driven tests for edge names (.en.srt, case, dots).

⑦ Fat rows & fat bitmaps: SELECT v.* drags ffprobe JSON + blobs into every page; thumbnails decode unconstrained

Strong

Files

  • lib/logic/catalog_controller.dart:163 — SELECT v.* pulls thumbnail_blob (legacy) + multi-KB ffprobe metadata_json for every loaded row, retained forever in provider state
  • lib/ui/widgets/video_grid.dart:1058–1062 — Image.file(...) with no cacheWidth/cacheHeight: full-decoded bitmaps cached at native resolution regardless of ~200 px cell size
  • lib/ui/widgets/video_grid.dart:816–840 — full jsonDecode of probe JSON on every hover-open

Solution

  • Slim projection for list queries (id, title, duration, size, addedAt, folderId, flags, thumbnailPath); fetch metadata/blob lazily where used.
  • cacheWidth: (cellWidth × devicePixelRatio).round() — one line, ~5–10× decode-memory cut.
  • Longer-term: promote the handful of useful ffprobe fields to columns; stop storing raw JSON in the hot row.

Benefits

  • depthThe Video data class stops being a dumping ground; snapshot memory scales with what the grid actually shows.
  • leverageEvery scroll, every page, every user benefits immediately; zero behavior change.

Top recommendation

Start with ① Fast-search foundations as one PR, then ② Grid fan-out

Candidate ① is the highest leverage-per-line-of-code in this report: a single migration adds the four indexes everything already wants, the debounce is ~10 lines, and slim-projection + cacheWidth are mechanical. Together they make search-and-browse feel instant at 10k videos and usable at 100k — with essentially zero behavioral risk.

Then tackle ② (stable per-id stream families, shared folders map, deferred freshness checks): it converts the grid's per-card-per-rebuild query storm into three shared seams, which is where the remaining jank lives.

The security card's #1 and #2 (ffmpeg argv array; bookmark entitlement) deserve their own small PRs first — each is minutes of work and #2 likely explains real user-facing “needs repair” pain today.
